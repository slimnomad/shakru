1.  Abstract
Green Asian Wok needs a clearer path from choosing food to placing an order. This proposal combines the website audit and review findings with a menu-led frontend, while retaining the existing ordering provider for checkout and fulfilment.
Evidence was collected on 10 October 2026. Three visual concepts are delivered separately. This is a proposed system design, not a shipped website or an assertion about provider capabilities. Operational contacts, schedules and integration access require confirmation.

3.  Background and Problem Statement
The current homepage prioritises a large food banner and app promotion. Desktop ordering then adds a fulfilment page and another banner before dishes. Maps and the site show different phone numbers; collection hours are difficult to interpret across midnight.
Google showed 4.5 stars from six ratings. Four visible written reviews praised flavour, value or portions; the visible two-star rating had no comment. Five individual records were exposed. These limited observations support honest dish discovery, not claims about delivery reliability.

5.  Request Lifecycle
A customer opens the homepage or menu. Browsing should work without an account or address; delivery and collection are explicit choices.
The frontend validates required item options and quantities. The provider validates current availability, service area and final prices at checkout.
Load a business-approved menu version, contact record and day-specific schedule. Treat unconfirmed operational data as unpublished.
Show dishes, prices and allergen information. Selecting a dish opens options and an updated total before adding it to the basket.
Store only a transient basket if supported. The provider remains responsible for durable order and payment records.
Handoff through a supported provider route. If an integration is unavailable, use its official ordering page and make that transition clear.
Only provider-confirmed success represents an accepted order. Measure menu engagement and successful handoff without recording personal payloads.

7. Consistency, Idempotency, and Replay
Repeated menu reads may be cached. Basket additions must not be duplicated by retries. Payment and order idempotency belong to the provider; this proposal does not assume undocumented provider guarantees. A failed handoff must never display order success.

8. Security and Privacy Considerations
Public browsing needs no login. Restrict menu publication to authorised staff; use provider-supported authentication for ordering administration.
Collect no address or phone number on the marketing site unless a supported flow requires it. Exclude payment, address and contact values from analytics.
Keep provider credentials server-side if an approved API is used. No secret belongs in browser code or static content.
Preview menu changes before publishing. Operational support views should expose only the data needed to resolve an issue.
The business and provider must confirm retention and privacy responsibilities. Keep analytics aggregate and document deletion and support routes before launch.

12. Decision and Next Steps
Recommended architecture: build the selected visual concept around a verified menu record and retain provider ordering. Confirm operational data, replace illustrative assets, implement interactions, then test the complete browse-to-handoff path. Release only after visual, accessibility and provider checks pass.
